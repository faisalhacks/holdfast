# Claims

What this project asserts, what it retracts, and where every number comes from.

A critic session ran roughly a dozen searches against our claim list in the last wave of the
build and broke most of it. The list below is what remains after that. It is narrower than
what this project was saying earlier in the day, and the narrowing is recorded rather than
quietly applied.

---

## The two claims we make

### 1. No cash-application vendor publishes a false-clear rate for its own auto-matched items

Accuracy is published. Medius publishes a First Time Right rate; Vic.ai publishes accuracy
figures; auditors publish improper-payment rates over re-reviewed production populations.
What is not published anywhere we could find is the rate at which a cash-application product
**confidently settled the wrong document** — the number that tells a controller what the
automation cost them.

Holdfast publishes it, per run, per stratum and per hold type, generated by a harness the
prose cannot edit. On the holdout it is zero over 24 strict auto-clears, with the structural
caveat in AF-1.

### 2. A tolerance change is recorded as a decision on the specific hold it released

**The narrow form only.** The incumbent ERP does record that a tolerance was reconfigured —
SAP logs it through change documents. What we could not find published anywhere is the change
bound to the **individual hold whose release it caused**.

In Holdfast, changing a tolerance writes a tolerance-change row and a paired decision that
name each other, plus two journal rows, and produces a per-hold assessment with three
outcomes:

- `released` — the change lifted this hold;
- `requires_named_release` — the tolerance governs the hold, but a person must still act;
- `withheld` — with one of five typed reasons.

A hold is released by a tolerance change only if all five conditions hold: the hold is open,
it is inside the declared scope, the tolerance kind actually reaches that hold type on a
declared basis, the change is a **widening**, and the hold's policy allows auto-release.
Direction is derived from the two values, never declared by the reviewer — and derived
correctly for the awkward case: a ceiling loosens as it rises, but a **similarity tolerance
is a floor**, so raising it registers as *narrowed*. Three independent implementations agree
on that derivation, one of them a generated database column.

`reconcileRelease` then answers the question the feature exists for: of the holds recorded as
released alongside this change, which were released **without** governance.

## What we explicitly do not claim

| | why |
|---|---|
| **Typed holds with auto-release and an accounting block are novel** | Oracle Payables ships hold codes, an accounting-hold reason, and a postable flag. SAP has blocking reasons with automatic release. **We port a data model. We did not invent one.** |
| **Ordering exceptions by money at risk is novel** | Trintech's risk-based reconciliation rates accounts by materiality. |
| **Resolution path plus owner-next is novel** | Stampli already frames it as *"a category, an owner, and a clock."* |
| **Three-way match, touchless AP or duplicate detection is novel** | Table stakes, submitted to hackathons repeatedly. It is a house rule in `AGENTS.md` that no worker may claim otherwise. |
| **We meet a production bank's match-precision requirement** | BenchRec records 99.8-99.9%. We floor ourselves at 0.98 and report what we observe. We adopt the principle; we do not claim the bar. |
| **A model contributed to any cleared or released outcome** | It structurally cannot. See the boundary section below. |
| **Any assurance-programme, attestation or certification-scheme status** | We make no such claims of any kind, and nothing in this repository is a security or audit-readiness statement. |
| **Anything about the reviewer UI** | It was built by a human collaborator outside AO. |

### Three sentences we retract

They were in our own pitch earlier in the build. They are false.

1. *"Nobody publishes how often they got it wrong."*
2. *"No audited error rate exists."*
3. *"Nothing records that a judgement was made when a tolerance changes."*

See `docs/adverse-findings.md`, AF-4, for the counter-examples in each case.

## The claim about the model boundary, and what backs it

**The model proposes; deterministic code verifies.** No model output can set a hold release
or a cleared state, directly or transitively.

What backs it, in order of strength:

1. **The database.** A model actor is confined by migration to exactly two journal events —
   a proposal received and a proposal discarded. A candidate cannot reach a cleared state
   unless it was re-verified. These are constraints, not conventions.
2. **The proposal schema.** Strict, and it admits exactly two fields: a list of payment ids
   and a citation enum drawn from a closed list. No amount, no score, no hold, no certainty.
   **There is no field anywhere in this codebase for a model's stated certainty**, and a
   build gate fails the repository if one is introduced under the engine, the boundary, the
   app or the shared library.
3. **The gate.** Every nomination re-enters the same scorer with the same weights and the
   same spec id as any deterministic candidate, and is discarded unless it clears the accept
   threshold on its own merits. The gate is deliberately blind to provenance. There are four
   named discard reasons and they are all recorded.
4. **A test.** One of exactly three tests in this repository walks the value-import graph out
   of the boundary and asserts that nothing reachable from it can express a release, a clear
   or a hold; that a nomination which does not stand is discarded; and that with no
   credentials the pass proposes nothing at all.

## Where every number comes from

Numbers in `README.md`, `DEVPOST.md` and `docs/**` pass in three cases and no others:

- **MEASURED** — the value is present in `eval/report.json`, produced by the harness.
- **CITED** — the value is present in `docs/citations.json` with a named source.
- **STRUCTURAL** — small prose counts, list numbering, dates, worker ids, fenced code.

`pnpm audit:claims` extracts every numeric token from those files and fails the build on
anything else, printing the token, the file and the line. Both the report and the citation
list are **frozen paths**: the branch that owns `docs/**` cannot edit its own citation list,
because the frozen check runs before the scope check. A number cannot reach this submission
unless we measured it or can say where it came from.

That gate is the reason the following sentence is worth anything: *we did not type a single
metric in this repository by hand.*
